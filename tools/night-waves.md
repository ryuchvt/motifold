# Optional capture waves

The recording guard defaults to serial release. Supported widths are exactly 1, 2 and 4. Only the local dev pool permits four execution slots; hosted public credit remains at three slots, and every pool cap and daily limit is unchanged.

An operator may add `--wave-width 2` or `--wave-width 4` to the existing `night-204` command only with `--start-worker --isolate-settled`. Use independent browser pages and hooks, with different recipe IDs. Do not run concurrent recipe choices on the same hook. The width limits simultaneous requests, including the normal A/B previews from a page.

A wave starts one request in the owned fresh runtime. Further requests may join while it remains open, including several seconds later. Queued paid requests fill its remaining slots even if a read-only GET is waiting. The wave seals at its configured capacity or its first terminal result, including a streamed result before the HTTP body closes or a local refusal. Requests arriving after sealing wait for the next wave. All released operations must finish before maintenance begins. If all are known and at least one made a fresh settled call, the guard restarts its one owned Worker once. Cache-only waves need no restart. A charged settled rejection follows the existing night-profile policy. An unknown, absent settlement or invalid charge freezes new paid work while the other already-released streams finish.

Read-only GETs queue behind the whole wave and its restart. The existing owned-Worker code waits for the old process and port to stop before starting its successor. No second Worker shares the SQLite ledger.

The same persistent approved-run file retains the $23 ceiling and all earlier attempts across restarts and width changes. Before every release, one readonly SQLite transaction snapshots the dev balance and all owned attempt rows. A durable owned reservation absent from that snapshot is added to session exposure and the pool and daily totals. Provisional reservations are never treated as free merely because their Worker row is not visible yet. A first reservation is persisted synchronously before another slot can be admitted. Existing holds, the public allowance and the personal reserve remain separate.

At the current worst-case reservation of about $1.48 per request, a four-slot wave may need almost $5.93 of headroom before any calls settle. Monitor reservation-inclusive headroom: below $6.2, drain and review using width 2; below $3.1, review width 1. These thresholds are conservative while requests remain in flight. Inspect actual settlements and retained unknown holds, and recompute headroom before restarting at a smaller width. Reuse the same approval file and output directory. Never reset the allowance or release unknown holds to make another wave fit.

The capture driver stops on a historical session-ceiling refusal. If one occurs, the operator must audit that receipt and confirm it was unsent before deciding whether to restart. Neither a width change nor a restart automatically retries a failed request or grants more money.

## Operator review of retained unknown charges

Every `night-204` startup refuses an owned uncertain hold unless the operator supplies `--review-uncertain <local audit.json>`. There is no audit generator, automatic acknowledgement or in-process resume. Stop and drain the guard first. Inspect the private receipts, retained approval file and ledger before deciding whether another explicit recording run is appropriate. This gate is only for the local recording operator.

The JSON must contain exactly `version` (1), `run`, `started`, `ceilingMicros`, `reviewedAt`, `uncertain`, `noPendingAttempts`, `noProvisionalAttempts` and `preserveEveryHold`. Copy the immutable run identity, original start and original $23 ceiling from the retained approval. Set the three confirmations to `true` only after that review. `reviewedAt` is the current ISO timestamp. `uncertain` lists every owned unknown hold exactly once as an object containing only `attemptId` and `reservationMicros`. Each UUID and full reservation must match both the retained approval and its current uncertain ledger row. Keep this operator-created file private and outside tracked source.

The guard independently takes a readonly startup snapshot. Any dev reservation or dispatch with an unexpired lease or no lease refuses startup even when the audit claims otherwise. Every unfinished owned attempt refuses startup regardless of its lease, as does a provisional owned reservation without a ledger row. Cache hits already recorded as no-charge may have no row. An expired unowned historical reservation or dispatch is excluded only from this activity check. It remains unresolved, untouched and fully counted in the dev pool and applicable daily exposure. `noPendingAttempts` confirms this activity check, not settlement of historical holds. An absent, stale, incomplete or mismatched audit never supplies a new allowance.

A valid review changes no attempt, state, charge, reservation, cap or approval. Every reviewed hold still counts at its full amount against the session, pool and daily limits. Only review metadata is appended to the private receipts. The operator must still start and arm a new guard explicitly. Any later unknown stops that guard, and an older audit cannot cover the new UUID on a subsequent restart. Nothing here retries or recovers a provider response.

The guard records wave IDs and slots alongside the existing call receipts. It forwards only explicit tagged capture requests and never retries them on its own. Four-stream behavior has local fake-upstream tests; the first actual four-stream wave still needs observation under the existing approved ceiling. This is not a production connection fix or a promise of proportional speed.
